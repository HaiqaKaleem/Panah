Purpose of this documentThis is the engineering build document for Panagah. It intentionally avoids generic business-plan material. It defines the actual MVP architecture, data flow, services, schemas, generation pipeline, 3D representation, validation engine, APIs, UI, testing and build order.
1. What We Are Actually Building
Panagah is a web application that takes a structured shelter request and produces a small number of 3D shelter-component candidates. The important technical property is that the generated candidate is converted into a machine-readable design object and then evaluated by a separate deterministic validation service.
USER INPUT  family + site + materials + environment                 ↓        CONSTRAINT BUILDER                 ↓          AI GENERATOR                 ↓      STRUCTURED DESIGN JSON                 ↓       GEOMETRY BUILDER                 ↓          3D VIEWER                 ↓     INDEPENDENT VALIDATOR                 ↓      PASS / FAIL / REVIEW                 ↓        ENGINEER REVIEW
2. MVP: Keep the Design Problem Small
Do not attempt to generate an entire house or a complete structural system in the first build. Pick one component family and make the whole pipeline work.

6. The Constraint Builder
The first backend operation is not AI generation. It is turning the user's form data into a clean constraint object.
{  "occupancy": {"people": 6},  "site": {"length_m": 6.0, "width_m": 5.0},  "materials": [    {"id": "MAT-01", "type": "bamboo", "qty": 24,     "length_m": 4.5, "diameter_m": 0.06}  ],  "environment": {"scenario": "configured_case"},  "design_target": "roof_truss",  "unknowns": []}
This object becomes the common input to both the AI generator and the validator. The AI sees it to design; the validator sees it to check.
7. AI Generation: How It Actually Works
The model should not be asked to invent a 3D mesh directly. For the MVP, the model generates a structured parametric design description. Our geometry service turns that description into the actual 3D representation.
ConstraintSet   ↓Prompt + JSON schema   ↓Model Studio / Qwen   ↓Candidate JSON   ↓JSON Schema validation   ↓Canonical DesignVersion
7.1 Example AI Output
{  "design_type": "roof_truss",  "span_m": 4.2,  "height_m": 1.0,  "members": [    {"id":"M1","type":"beam","length_m":4.2,"material_id":"MAT-01"},    {"id":"M2","type":"brace","length_m":2.3,"material_id":"MAT-01"}  ],  "connections": [    {"a":"M1","b":"M2","type":"bolted"}  ]}
The model may propose the topology and dimensions, but the application owns the schema, units, allowed component types and validation status.
8. Parametric 3D Generation
Once the design JSON is accepted, the geometry service creates the visual model. This is more reliable than asking the LLM to output arbitrary mesh data.
Design JSON   ↓Component factory   ├── beam(length, diameter)   ├── panel(width, height, thickness)   ├── connector(position, type)   └── brace(start, end)   ↓Three.js scene   ↓GLB/GLTF + interactive viewer
Each component keeps its component_id and material_id so the UI can highlight the exact physical element associated with a validation failure.

10. Validation Engine Architecture
validator/├── engine.py├── context.py├── aggregation.py├── rules/│   ├── geometry.py│   ├── materials.py│   ├── load_path.py│   ├── environment.py│   └── connections.py└── tests/
Each rule is a normal function/class. It receives a validated DesignVersion plus a ValidationContext and returns a structured ValidationResult.
11. Validation Context
ValidationContext = {  "design": canonical_design,  "site": site_data,  "materials": material_data,  "environment": environment_data,  "rule_set_version": "1.0.0"}
The validator never calls the LLM to decide the result.

Engineering boundaryThe first implementation should only encode rules that the team can define and justify. Do not fabricate structural formulas just to make the demo look scientific. Where a real engineering capacity calculation is outside the MVP, return REVIEW.
13. Example Deterministic Rule
A simple material-inventory rule is fully deterministic:
required_quantity = sum(component.quantity_required)available_quantity = material.quantityif required_quantity > available_quantity:    FAILelse:    PASS
A geometry rule follows the same pattern:
if design.span_m > configured_max_span_m:    FAILelse:    PASS
More advanced structural calculations should be added only after their engineering assumptions, equations, units and sources have been reviewed.
14. Rule Registry
rules/v1/  R-GEO-001.yaml  R-MAT-001.yaml  R-MAT-002.yaml  R-ENV-001.yaml  R-CON-001.yaml
Each rule file should contain: rule_id, version, severity, inputs, units, logic reference, source/reference, assumptions and test cases.
rule_id: R-MAT-001version: 1.0.0severity: HIGHtype: HARDname: Material quantity availableinputs: [required_quantity, available_quantity]assumptions:  - Quantity is measured in the same unit
15. Result Aggregation
if any HARD rule == FAIL:    overall = FAILelif any MANDATORY rule == REVIEW:    overall = REVIEWelif any rule == ERROR:    overall = ERRORelse:    overall = PASS
The frontend receives the result; it does not calculate it.

18. The Main Demo Case
The demo should be engineered around a controlled pair of candidates.
CASE INPUT6 people / 6×5 m site / bamboo inventory             ↓       CANDIDATE A       naive geometry             ↓       VALIDATOR             ↓       FAIL   ├─ span exceeded   ├─ material quantity exceeded   └─ connection review required             ↓      REGENERATE             ↓       CANDIDATE B             ↓       VALIDATOR             ↓ AUTOMATED CHECKS PASSED   + REVIEW: engineer check             ↓       ENGINEER DECISION
This is much stronger than showing a beautiful 3D render because it demonstrates that the system actually reacts to constraints.

23. What Is Explicitly NOT Being Built
A fully autonomous structural engineer.
A replacement for professional engineering approval.
A complete building-code certification engine.
A full finite-element analysis platform.
A nationwide disaster-management system.
A generic AI chatbot with a 3D model attached.
24. Final Technical Definition
PanagahA constraint-driven generative design system in which a web application collects field requirements, converts them into a canonical constraint model, uses Alibaba Cloud AI to generate structured shelter-component candidates, converts those candidates into parametric 3D geometry, and independently evaluates the same canonical design through a deterministic validation engine before presenting the evidence to a human engineer.
25. Definition of a Successful MVP
One real shelter component can be generated end-to-end.
The generated design exists as structured JSON, not only an image.
The same design JSON drives both the 3D viewer and validator.
At least three meaningful deterministic validation rules work.
A deliberately bad candidate visibly fails.
A constrained candidate can pass the implemented checks.
Every result identifies the rule and evidence behind it.
An engineer can review the candidate and record a decision.
The complete workflow can be reproduced from a clean project.
